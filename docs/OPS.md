## 1. 运维职责概述

本工作流部署在 n8n 上运行。运维人员负责：
- 部署与激活工作流。
- 监控执行状态与成功率。
- 故障排查与恢复。
- 凭据与站点配置维护。

---

## 2. 部署

### 2.1 导入工作流
- 方式一（编辑器）：n8n → **Workflows** → **Import from File** → 选择 `workflows/tech-content-wordpress-publish.json`。
- 方式二（CLI，自托管）：
  ```bash
  n8n import:workflow --input=workflows/tech-content-wordpress-publish.json
  ```

### 2.2 绑定凭据
导入后，为以下节点重新绑定凭据（ID 在新实例可能不同）：
- **DeepSeek Chat Model** → `deepSeekApi` 凭据。
- **HTTP - 创建分类 / HTTP - 创建标签 / HTTP - 创建文章** → `wordpressApi` 凭据。

### 2.3 激活
1. 点击 **Execute workflow** 手动测试一次。
2. 确认发布成功、分类/标签正确。
3. 点击右上角 **Active** 开关激活。

> **重要**：n8n Public API 无法远程激活工作流（`active` 字段只读），必须人工在编辑器激活。

---

## 3. 监控

### 3.1 执行状态
- 在 n8n 打开工作流 → **Executions** 查看最近执行。
- 关注：每 6 小时应有 1 次执行；失败需定位节点。

### 3.2 关键指标
| 指标 | 正常值 | 异常处理 |
|------|--------|----------|
| 执行频率 | 每 6 小时 1 次 | 检查 Active 开关、Schedule Trigger |
| 发布成功率 | 接近 100% | 查看失败节点与错误信息 |
| 文章产出 | 每日 4 篇 | 偏低时检查 AI 调用/限额 |

---

## 4. 备份与恢复

### 4.1 备份
- 工作流 JSON 已在仓库 `workflows/` 中托管，即天然备份。
- 建议定期 `git pull` 保持本地副本最新。

### 4.2 恢复
- 从仓库重新导入工作流 JSON。
- 重新绑定凭据并激活。

---

## 5. 故障排查

### 5.1 工作流不执行
- 确认 **Active** 已开启。
- 确认 Schedule Trigger 频率配置正确。
- 查看 Executions 是否为空。

### 5.2 发布失败
- 检查 WordPress 凭据是否有发布权限。
- 检查站点地址是否可达、REST API 是否启用。
- 查看失败节点错误信息。

### 5.3 分类/标签创建失败
- 检查词条是否已存在（创建返回冲突属正常，需解析 term_id）。
- 检查 `Code - 取得分类ID` / `Code - 重组标签ID` 是否报错。

### 5.4 AI 输出解析失败
- 查看 `Code - 解析AI输出` 报错信息。
- 可能是 DeepSeek 输出格式异常或额度不足。

## 6. 常见运维操作

| 操作 | 方法 |
|------|------|
| 调整发布频率 | 改 Schedule Trigger 的 hoursInterval，保存并重新激活 |
| 切换站点 | 修改 4 个含域名的 HTTP 节点的 URL；站点不同需换 WordPress 凭据 |
| 暂停发布 | 关闭工作流右上角 **Active** 开关 |
| 立即试跑 | 点击 **Execute workflow** |

---

## 7. 安全与合规

- 凭据仅存于 n8n 凭据系统，勿提交到仓库。
- 工作流 JSON 中记录的凭据 ID 属实例内部信息，公开仓库中若介意可导入后重新绑定。
- 发布内容真实性依赖提示词约束，高风险场景建议增加发布前人工审核。

---

## 8. 联系方式与排班

- 本工作流为单点部署，无多实例调度。
- 如遇持续失败，参照本文档排查，必要时联系工作流维护者。
